# PeekMoment 第一周进度汇报稿

小组成员依次发言

## M1 平台集成与整体进展

老师、同学们好，下面由我们小组汇报 PeekMoment 项目第一周的开发进展。我们会按照各自的分工依次介绍，我先说明整体情况，以及我负责的平台集成部分。

PeekMoment 的用户通过小程序发布和浏览动态，管理员通过管理端查看用户和内容。第一周，我们重点推进的是这两端共同依赖的基础工作，并且用一条“校园”动态串起了联调流程。这条动态从小程序发布后，游客可以在广场读到，管理员登录后也可以通过接口查到同一个编号。目前，这条流程已经在模拟服务上跑通。

我负责的第一部分是服务端工程和数据库初始化。本周已经搭好了服务端工程，编写了建表脚本，为动态、标签和媒体等数据提供统一的组织基础。这样，负责内容和管理功能的同学可以围绕同一套数据结构继续开发，后续联调时也能够对应到相同的记录。

第二部分是接口约定。我把本周涉及的六个接口的字段、分页方式和返回规则统一了下来。比如，前端需要知道发布时提交哪些信息，读取列表时怎样请求下一页，以及收到结果后怎样找到要展示的数据。这些内容确定以后，大家就可以按照同一份接口文档开发。

另外，模拟服务现在可以通过一条命令启动，方便各模块进行联调。小程序可以用它验证发布和读取，管理端接口也可以围绕同一条测试记录进行查询。这让我们能在开发过程中直接检查各部分是否衔接起来。

第一周的平台集成工作已经为各模块提供了共同的开发基础。接下来，请负责小程序内容的同学介绍用户这一侧的具体进展。

## M2 小程序内容与页面流程

大家好，我负责小程序的内容部分。本周，小程序初版已经通过 PR #1 合入主分支，包含登录页、个人中心和本机发布流程，初步搭起了用户操作的页面结构。

从使用过程来看，登录页是用户进入账号相关操作的入口，个人中心承担个人相关功能的入口，发布流程则对应用户编辑内容、发出动态的主要操作。这一版把这些页面和本机发布过程放到了一起，方便我们围绕用户的实际使用顺序继续完善功能。

在此基础上，我还在开发版中补充了用于联调的广场。现在可以通过这一部分向模拟服务发布文字，再把动态按页读取回来。这样，我们能够用一次实际的发布操作，检查小程序提交的数据和接口返回的数据是否对应，也能观察新内容在广场中的展示情况。

这次联调使用的就是前面提到的“校园”动态。发布后，我们可以在广场中找到它，再继续读取后面的内容。分页读取让列表可以分批展示动态，也为后续接入更多测试内容准备好了基础。

初版合入主分支后，组内其他同学也可以基于同一份小程序代码继续对接。接下来，我会配合正式登录和文件服务的接入，把已经准备好的页面、内容发布和附件处理进一步连接起来，让用户可以顺着页面完成一次完整的操作。

我的部分主要是这些页面和发布、读取流程。动态在提交后如何保存，下面请负责内容后端的同学继续介绍。

## M3 内容后端与数据组织

大家好，我负责内容后端。本周主要完成了动态发布的数据处理，以及游客广场读取公开动态的相关逻辑。

一条动态除了文字，还可能带有标签和图片。因此，发布接口需要把动态本身、标签和媒体之间的关系保存下来。后面再读取这条动态时，就能够根据这些关系，找到属于它的标签和附件，把一条内容完整地组织出来。

在保存过程中，我还保留了标签和图片的顺序。比如，用户发布几张图片时，通常会按照自己想表达的顺序排列。后端保存这一顺序，前端再读回来时，就可以按照发布时的次序展示。标签同样保留顺序，方便前后端对应同一份内容。

广场读取方面，游客看到的是公开动态，列表按照发布时间倒序排列，让新发布的内容出现在前面。结合分页读取，小程序可以一页一页地获取内容，服务端则按照统一的规则组织返回结果。

目前，模拟联调中的动态能够从发布进入广场读取流程，也可以在管理端接口中按相同的编号查到。通过这条记录，我们可以检查发布、展示和管理所使用的数据是否对应。接下来，我会继续配合小程序和文件服务的对接，完善完整的内容发布流程。

## M5 管理端接口

大家好，我负责管理端接口。本周主要完成了管理员查询用户和查询动态的相关接口，并且配合小程序的发布流程进行了数据核对。

用户查询方面，管理员登录后，可以按照昵称或用户编号查找用户，也可以通过分页逐步查看记录。昵称适合在知道用户名称时进行查找，编号则方便定位具体的用户。分页返回可以让管理端根据需要分批获取数据，后续页面对接时也有明确的读取方式。

动态查询方面，现在支持按照标题、作者或动态编号进行查找。这样，管理员既可以从内容本身入手，也可以根据发布者或者一条明确的记录来定位动态。这几个条件对应了不同的查询场景，能够为管理页面提供基本的数据查找能力。

本周联调时，我们把广场中新发布的测试动态拿到管理端接口进行查询，能够找到同一个编号。这个结果说明，用户侧发布的内容和管理侧查询到的记录能够对应起来。后续展示管理功能时，也可以沿用同一条测试记录，从发布过程一直查看到管理查询结果。

我的工作主要在接口层，提供管理页面需要的查询数据。接下来会配合 Web 管理前端对接这些接口，核对查询条件、分页参数和返回字段，让页面上的操作能够获取到相应的数据。

管理端接口的部分先介绍到这里，下面请负责小程序上传的同学介绍图片和附件处理的进展。

## M6 小程序图片与附件处理

大家好，我负责小程序上传相关的工作。本周主要完成的是发布页的图片预处理、附件处理数量控制，以及处理结果和图片顺序的保留。

用户在发布页选择图片之后，流程会先对图片进行压缩，再进入后续处理。这样可以先在小程序一侧整理要提交的图片，为后面接入文件服务做好准备。当前演示中，文件保存在本机，可以用来验证选图、压缩和发布之间的衔接。

附件处理方面，目前同时最多处理三个附件。用户选择多张图片时，会按这个数量限制安排处理。这里的“三个”指同时处理的数量，重点是让多附件的处理过程按照明确的规则进行。

另外，附件处理已经加入单项重试机制，同时会保留其他已经完成的结果和原有顺序。对于多张图片的发布，这样就能继续使用已经准备好的附件。后续将附件信息交给发布流程时，也可以继续沿用用户原先安排的图片顺序。

这部分工作和小程序内容、内容后端都有联系：小程序发布页负责让用户选择和编辑内容，我这里负责把附件整理好，后端再保存动态和媒体之间的关系。三部分连接起来以后，图片就能跟随对应的动态进入完整的发布流程。

下一步，我会把现有的图片和附件处理接入真实文件服务，再配合内容发布和微信真机验证。我的部分汇报完毕，下面请负责测试和加分项预研的同学介绍本周的验证结果。

## M7 测试验证与下周安排

大家好，我负责测试和加分项预研。本周的测试主要围绕动态发布、广场读取和管理端查询这条流程展开，重点检查各模块连接起来以后，输入和返回的数据是否符合接口约定。

首先，我们整理了 P0 测试用例，也就是当前需要优先保证的核心流程，并准备了 Apifox 测试集合。后续接口发生调整时，可以继续使用这套集合重复检查，把测试结果和预期放在一起对照。

模拟服务方面，本周执行了 12 个 HTTP 请求，包含的 21 条断言全部通过。这些断言用于检查请求得到的结果是否符合预期，也为前面几位同学介绍的模拟联调流程提供了具体验证结果。

数据库方面，我们另外完成了 21 项 H2 检查，覆盖重复建表、分页顺序和隐藏动态的可见范围。重复建表检查关注初始化脚本能否重复执行；分页顺序检查关注动态列表是否按照约定返回；可见范围检查则关注隐藏动态与公开展示之间的规则。这部分检查帮助我们核对数据组织和读取逻辑。

同时，后端已经编写了 7 组 JUnit 测试，为后续持续验证作了准备。测试用例和接口测试集合会随着功能推进继续补充，方便每次调整之后检查核心流程。

加分项方面，本周完成了敏感词审核和摘要相关处理方案的整理。当前这部分属于预研，我们先明确这些能力怎样与内容流程衔接，作为后续扩展时的参考。

接下来一周，小组会继续把正式登录、真实文件上传和内容发布串起来，再用微信真机走一遍完整流程。同时配合 Web 管理前端进行接口对接，并继续安排自动化测试和 MySQL 8 数据库验证。

第一周，我们已经搭好了共同的开发基础，小程序初版完成合入，内容和管理接口能够围绕同一条测试动态进行联调，附件处理和核心测试也都有了具体产出。以上就是我们小组本周的进展汇报，谢谢老师和同学们。
